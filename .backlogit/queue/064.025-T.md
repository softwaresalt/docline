Author the failing shared-fetch request-amplification harness in the fetch test suite (tests/fetch/) (test-first / red). Tests domain only. Cycle-8 (PR #166 round-2) review found max_pages does NOT bound actual fetch work: the crawl loop (src/docline/fetch/crawl.py) fetches print pages, duplicate final URLs, and out-of-scope-section final URLs and enqueues their links WITHOUT incrementing page_count - the `_is_print_page(final_url, ...)` branch, the `final_key in emitted_urls` duplicate branch, and the `crawl_config.domain_lock and not _url_within_section_scope(final_url, section_scope)` branch each `continue` without `page_count += 1`, while every frontier pop performs a real network fetch via `_fetch_with_retries`. Because FetchRequest.depth has no upper bound (src/docline/app_models.py:24 `Field(default=0, ge=0)`, flowed into CrawlConfig.max_depth at src/docline/app.py:606), an attacker can chain tiny under-cap `/print` pages and trigger far more than MAX_PAGES_LIMIT actual requests while staying below the per-response and aggregate BYTE budgets (those bound transfer volume, NOT request COUNT). This harness pins the hard request-amplification bound (a fetch-attempt/frontier cap plus a depth upper bound) on the SHARED fetch code (affects CLI docline fetch and the MCP fetch tool). See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H7 item 4).

<!-- BEGIN:acceptance-criteria -->
- Fetch-attempt amplification via the non-counting branches: a BRANCH-ACCURATE fake/instrumented transport drives the crawl to abort with a typed error (a DoclineError subclass) once the total fetch attempts - frontier pops / actual main-page fetches, counted on EVERY pop REGARDLESS of page_count - reach the hard cap MAX_FETCH_ATTEMPTS = 4000 (plan §H7 Selected numeric limits), while page_count stays below max_pages. The harness exercises EACH of the three non-counting branches with a setup that matches real crawler behavior (only the print branch enqueues links; the duplicate and out-of-scope branches `continue` before link extraction, so their pops are seeded from a preloaded frontier): (i) PRINT - each print response naturally enqueues a fresh in-scope link (self-sustaining frontier); (ii) DUPLICATE - an emitted page preloads many distinct alias request URLs that each redirect (response.url) to an already-emitted final URL, hitting the `final_key in emitted_urls` branch; (iii) OUT-OF-SCOPE - an emitted page preloads many distinct in-scope request URLs that each redirect to an out-of-section final URL, hitting the `not _url_within_section_scope(final_url, ...)` branch. Asserts total transport fetches are bounded by MAX_FETCH_ATTEMPTS even though page_count stays below max_pages - proving the counter increments in those branches, not only on emitted pages. Boundary: exactly 4000 fetch attempts are allowed; the 4001st is refused (the crawl raises, it does NOT silently return the accumulated skipped results).
- Depth upper bound: FetchRequest.depth above the hard upper bound MAX_DEPTH_LIMIT = 64 (i.e. >= 65) is rejected at model validation (ValidationError / -32602 on the MCP boundary); depth 0..64 inclusive is accepted; AND a request OMITTING depth still validates (depth defaults to 0, so the Field bound stays Field(default=0, ge=0, le=64) and does not make depth required) (plan §H7 Selected numeric limits).
- All new tests observed FAILING before implementation (red) - no fetch-attempt cap and no depth upper bound exist yet.
- Scenario budget: 2 (fetch-attempt amplification via the non-counting branches; depth upper-bound rejection incl. omit-depth default) - within the <4 heuristic.
