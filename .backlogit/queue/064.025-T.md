Author the failing shared-fetch request-amplification harness in the fetch test suite (tests/fetch/) (test-first / red). Tests domain only. Cycle-11 (PR #166) review REJECTED the frontier-pop mechanism: a MAX_FETCH_ATTEMPTS counter incremented only on main-page frontier pops (src/docline/fetch/crawl.py) does NOT bound actual outbound requests, because robots.txt (`_robots_allow`), mdBook TOC-script (`_discover_toc_links`), per-pop retries (`_fetch_with_retries` issues a fresh `fetch_page` per attempt), and redirect hops (`_ValidatingRedirectHandler`) are all real outbound requests that bypass a frontier-pop counter, and the per-response/aggregate BYTE budgets bound transfer VOLUME not request COUNT (empty/tiny robots/TOC responses barely spend the byte budget). This harness instead pins a request-scoped fetch-ATTEMPT budget on the shared `RemainingByteBudget`: EVERY direct outbound request - main pages, robots, TOC, retries (each a distinct `fetch_page` call) - decrements ONE per-request allowance debited BEFORE the request at the COMMON `fetch_page` boundary (src/docline/fetch/http.py); redirect hops are debited per-hop INSIDE the shared `_ValidatingRedirectHandler` (in redirect_request, after validation, before outbound I/O) and are proven by the redirect-hop attempt-debit harness 064.029-T (this harness covers robots/TOC/retries). Plus a depth upper bound at the model (still on the SHARED fetch code - CLI docline fetch and the MCP fetch tool). Because FetchRequest.depth has no upper bound (src/docline/app_models.py:24 `Field(default=0, ge=0)`, flowed into CrawlConfig.max_depth at src/docline/app.py:606), the depth vector is closed at model validation. See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H7 item 4, cycle-11).

<!-- BEGIN:acceptance-criteria -->
- Outbound-attempt budget at the common boundary: a fake/instrumented transport drives the crawl to abort with a typed error (a DoclineError subclass - `FetchAttemptBudgetExceededError`, a subclass of `AggregateBudgetExceededError` so it rides the existing crawl.py re-raise clauses) once the TOTAL outbound fetch attempts across the request - each debited BEFORE its outbound call at the `fetch_page` boundary (pre-I/O) - would cross the hard cap MAX_FETCH_ATTEMPTS = 4000 (plan §H7 Selected numeric limits), even while page_count stays below max_pages. The harness proves AUXILIARY and RETRY traffic ALONE cannot bypass the cap: (i) ROBOTS - enabling robots.txt fetching issues `_robots_allow` `fetch_page` calls that each debit the budget; (ii) TOC - mdBook TOC-script discovery issues `_discover_toc_links` `fetch_page` calls that each debit the budget; (iii) RETRIES - transient failures make `_fetch_with_retries` issue multiple `fetch_page` calls per pop, each debiting one attempt. (The redirect-hop attempt debit - one per hop inside the shared `_ValidatingRedirectHandler`, in redirect_request after validation - is proven by 064.029-T, not here.) A crawl whose emitted page_count stays LOW but whose robots/TOC/retry outbound traffic is HIGH still trips MAX_FETCH_ATTEMPTS - proving the budget counts every outbound request, not just main-page pops. Boundary: the first 4000 debits succeed; the debit that would cross the cap is refused BEFORE its outbound I/O (the crawl RAISES; it does NOT silently return the accumulated skipped results).
- Depth upper bound: FetchRequest.depth above the hard upper bound MAX_DEPTH_LIMIT = 64 (i.e. >= 65) is rejected at model validation (ValidationError / -32602 on the MCP boundary); depth 0..64 inclusive is accepted; AND a request OMITTING depth still validates (depth defaults to 0, so the Field bound stays Field(default=0, ge=0, le=64) and does not make depth required) (plan §H7 Selected numeric limits).
- All new tests observed FAILING before implementation (red) - no outbound-attempt budget at the boundary and no depth upper bound exist yet.
- Scenario budget: 2 (outbound-attempt budget incl. robots/TOC/retry boundary coverage - redirect-hop coverage lives in 064.029-T; depth upper-bound rejection incl. omit-depth default) - within the <4 heuristic.
