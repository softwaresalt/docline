Author the failing shared-fetch SSRF-by-resolution harness in the fetch test suite (tests/fetch/) (test-first / red). Tests domain only. Cycle-2 review found that fetch/url_policy.py is_private_host does NOT resolve hostnames (src/docline/fetch/url_policy.py:50-56) before urllib connects (src/docline/fetch/http.py:116-123), so a public hostname resolving to a non-public-unicast address bypasses the guard on the newly untrusted MCP fetch surface. This harness pins the required resolution/connect-time behavior on the SHARED fetch code (affects CLI and MCP). See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H6).

<!-- BEGIN:acceptance-criteria -->
- Initial URL whose public hostname resolves to a non-public-unicast address is rejected before connect (mock DNS resolution). Parametrize the rejected address forms to cover the class predicates of _is_unsafe_address (src/docline/fetch/sitemap.py:173-189) plus the explicit CGNAT check H6 adds on top: 127.0.0.1 (loopback), 10.0.0.1 (private), 169.254.0.1 (link-local), 169.254.169.254 (metadata), 224.0.0.1 (multicast), 240.0.0.1 (reserved), 0.0.0.0 and :: (unspecified), CGNAT 100.64.0.1 (100.64.0.0/10 - caught by none of is_private/is_reserved/is_global on Python 3.12.x, so an explicit membership check is required), ULA (fc00::/7), plus normalization-bypass forms - IPv4-mapped IPv6 (::ffff:127.0.0.1, ::ffff:224.0.0.1, ::ffff:100.64.0.1) which MUST be normalized to the embedded IPv4 form BEFORE any class predicate (mapped multicast/CGNAT/reserved do not trigger the IPv6-form predicates). Any address ipaddress cannot classify is treated as unsafe (fail closed). Because ipaddress special-purpose tables are Python-patch-dependent (CVE-2024-4032 hardened is_private in 3.12.4), test-pin each security-critical class explicitly rather than trusting the installed flag table. These multicast/reserved/unspecified/CGNAT/mapped forms are additional parametrized address inputs to the single initial-URL-resolution scenario, so the scenario budget stays 3 (<4).
- A redirect target whose hostname resolves to a private address is rejected mid-chain at connect time (not merely a netloc compare of the final URL).
- Address-pinned connect / DNS-rebinding (parametrized): (i) when validation-time resolution and connect-time resolution differ (rebinding), the connection uses the VALIDATED address (no second unvalidated lookup), and any private address in the validated A/AAAA record set is rejected; (ii) with HTTP(S)_PROXY environment variables set, the fetcher does NOT delegate resolution to an inherited proxy (empty ProxyHandler / disabled env proxies) so no second, unvalidated proxy-side DNS resolution of the original hostname can occur. Also assert the pinned connect preserves the Host header / SNI so TLS cert validation still targets the hostname.
- All new tests observed FAILING before implementation (red) - the resolution/pinned-connect guard does not yet exist.
- Scenario budget: 3 (initial-URL resolution, redirect resolution, address-pinned/rebinding) - within the <4 heuristic.
