Author the failing shared-fetch SSRF-by-resolution harness in the fetch test suite (tests/fetch/) (test-first / red). Tests domain only. Cycle-2 review found that fetch/url_policy.py is_private_host does NOT resolve hostnames (src/docline/fetch/url_policy.py:50-56) before urllib connects (src/docline/fetch/http.py:116-123), so a public hostname resolving to loopback/private bypasses the guard on the newly untrusted MCP fetch surface. This harness pins the required resolution/connect-time behavior on the SHARED fetch code (affects CLI and MCP). See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H6).

<!-- BEGIN:acceptance-criteria -->
- Initial URL whose public hostname resolves to a loopback/private/link-local/metadata address (e.g. resolves to 127.0.0.1 or 169.254.169.254) is rejected before connect (mock DNS resolution).
- A redirect target whose hostname resolves to a private address is rejected mid-chain at connect time (not merely a netloc compare of the final URL).
- Address-pinned connect / DNS-rebinding: when validation-time resolution and connect-time resolution differ (rebinding), the connection uses the VALIDATED address (no second unvalidated lookup), and any private address in the validated A/AAAA record set is rejected. Also assert the pinned connect preserves the Host header / SNI so TLS cert validation still targets the hostname.
- All new tests observed FAILING before implementation (red) - the resolution/pinned-connect guard does not yet exist.
- Scenario budget: 3 (initial-URL resolution, redirect resolution, address-pinned/rebinding) - within the <4 heuristic.
<!-- END:acceptance-criteria -->
