Make 064.016-T green. Code domain only, <=2 files (fetch/http.py, fetch/crawl.py). Two coupled changes: (1) add FetchResponse.body_byte_count:int (with a DEFAULT so the frozen dataclass stays valid - FetchResponse's last field redirect_count:int=0 already carries a default, so body_byte_count MUST be declared body_byte_count:int=0 or inserted before redirect_count; a non-default field appended after a defaulted one raises TypeError at import and would break the whole fetch/parity suite) set from the length of the bytes read by the bounded reader BEFORE decoding (the body_bytes already materialized by the streamed read in 064.013-T) - the accurate raw wire count for per-response accounting/observability; (2) enforce the aggregate MAX_TOTAL_FETCH_BYTES budget (MAX_TOTAL_FETCH_BYTES = 512 MiB / 536870912 bytes; see plan §H7 Selected numeric limits) with a REQUEST-SCOPED remaining-byte budget THREADED into fetch_page and its bounded reader, decremented WHILE CHUNKS ARE READ, so the budget is enforced during transfer rather than summed after a successful FetchResponse returns. A post-return crawl accumulator is insufficient: the response that crosses the budget has already been fully read, and bytes from failed per-response reads retried by _fetch_with_retries never return a FetchResponse to accrue. fetch/crawl.py seeds ONE request-scoped budget per crawl request and passes it through the main-page and retry fetch_page calls - main pages and retries - so main + retry transfer for the request decrements the same budget; the ancillary robots.txt (_robots_allow) / mdBook TOC (_discover_toc_links) fetch_page calls are threaded onto that SAME budget by split successor 064.024-T (cycle-6 split, PR #166 review), so all transfer for the request ultimately decrements one budget. Isolated from 064.013-T so the shared-model (FetchResponse) blast radius and byte-accurate during-read accounting land in one bounded task. Cross-interface (CLI crawl too). See plan H7 item 3 / cycle-3 + cycle-4 + cycle-6 remediation.

<!-- BEGIN:acceptance-criteria -->
- FetchResponse gains body_byte_count:int WITH A DEFAULT (body_byte_count:int=0, or placed before the defaulted redirect_count field), set from len(body_bytes) captured BEFORE body_bytes.decode(...) in fetch/http.py fetch_page (the raw wire byte count, not len(body) or len(body.encode())). Existing FetchResponse constructors that omit it must remain callable.
- The aggregate budget is enforced by a request-scoped remaining-byte budget threaded into fetch_page and its bounded reader. The reader caps EACH individual read size at min(CHUNK_SIZE, per_response_remainder + 1, aggregate_remainder + 1) - the smaller of the per-response MAX_RESPONSE_BYTES remainder and the request-scoped aggregate remainder, each plus one - then consumes and COUNTS the actual bytes returned, decrementing BOTH the per-response and the aggregate allowances by that actual count. Because no read is ever requested larger than the tightest remaining allowance plus one, at either boundary only the SINGLE crossing byte can be pulled from the socket - NOT a full extra CHUNK_SIZE chunk. It aborts the read MID-STREAM by raising AggregateBudgetExceededError the moment a read returns a byte beyond the aggregate allowance (the crossing response is never fully buffered). The budget is seeded at MAX_TOTAL_FETCH_BYTES = 512 MiB (536870912 bytes) per crawl request (plan §H7 Selected numeric limits). Boundary: a total of exactly 536870912 raw wire bytes across the request is allowed; the read that would exceed it transfers at most one additional (crossing) byte and is aborted mid-stream. AggregateBudgetExceededError is a DoclineError subclass (typed-error convention; maps to the MCP boundary's DoclineError handling). The budget defaults to unbounded/None for a standalone single fetch so existing CLI single-fetch callers are unaffected.
- Every core consumer decrements the SAME request-scoped budget while reading: main-page reads and over-cap attempts that raise and are retried by _fetch_with_retries (retried bytes are counted, not free). The ancillary robots.txt / mdBook TOC fetch consumers are threaded onto the SAME budget by split successor 064.024-T (cycle-6 split), not in this task.
- Abort propagation (blocking): because AggregateBudgetExceededError subclasses DoclineError, it would be SWALLOWED by crawl.py's broad `except (DoclineError, OSError)` handlers. This task re-raises it at the TWO core broad-handler sites - crawl() main loop (~line 178) and _fetch_with_retries (~line 382) - by adding `except AggregateBudgetExceededError: raise` immediately before each broad handler, mirroring the existing `except CrawlUrlRejectedError: raise` pattern. (The remaining two ancillary re-raise sites - _robots_allow ~line 406 and _discover_toc_links ~line 465 - are owned by split successor 064.024-T.) The budget error MUST propagate cleanly out of crawl() as a RAISE (not be recorded as a per-page skipped CrawlResult, which would let the crawl continue over the remaining frontier with budget=0 and degrade a byte-abort into a max_pages x backoff time-exhaustion).
- 064.016-T scenarios (a) non-ASCII multibyte, (b) invalid-byte, (c)(i) main-page mid-read abort, and (c)(ii) retried-failure accrual pass green (crawl() RAISES rather than returning skipped results). The ancillary-fetch sub-vector 064.016-T scenario (c)(iii) is greened by split successor 064.024-T.
- Existing tests/fetch suite remains green (body_byte_count is additive with a default; the threaded budget defaults to unbounded for existing callers). Typed errors only; no bare except.
