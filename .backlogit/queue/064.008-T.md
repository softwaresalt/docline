<!-- BEGIN:acceptance-criteria -->
- A subprocess test (matching tests/parity/test_manifest_parity.py::test_python_m_docline_cli_runs_main) launches python -m docline.mcp / docline-mcp via subprocess.Popen with stdin AND stdout as pipes and keeps stdin OPEN across frames. It sends and FLUSHES one JSON-RPC frame (the modern server/discover probe, or the legacy initialize), then REQUIRES and reads that frame's response BEFORE sending the next frame (tools/list), reads the tools/list response too, and only THEN closes stdin (EOF) and awaits a clean exit. This interactive send->flush->require-response->send-next sequence detects a LIVE stdio deadlock - a greedy/buffered server-side read that waits for a full CHUNK_SIZE after a short frame, or a block-buffered stdout that withholds a response until the pipe closes - which an EOF-first "write everything then read" test masks by closing stdin first.
- Each response read is bounded by a timeout so a deadlock FAILS the test deterministically (it does not hang the suite); reading the response must not require closing stdin first.
- Asserts clean exit code + the tool names in the tools/list response match the advertised MCP tool set (docline --manifest minus the excluded ingest_local_dir).
- Test observed FAILING before the entry point exists (red), because src/docline/mcp/__main__.py and the [project.scripts] entry are not yet present.
- Scenario budget: 1 (interactive subprocess smoke) - within the <4 heuristic.
