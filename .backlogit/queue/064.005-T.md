- Error envelopes asserted as one parametrized scenario: -32700 (parse error / invalid JSON, INCLUDING Python's permissive non-finite JSON constants NaN, Infinity, and -Infinity - e.g. a frame {"jsonrpc":"2.0","id":NaN,"method":"ping"} and bare-token variants each return -32700 with id:null, proving the strict parse_constant rejection so a non-finite float never passes the id-type guard nor reaches response serialization), -32600 (invalid request), -32601 (method not found), -32602 (invalid params), -32603 (internal).
- -32600 request-shape validation (bounded parametrized cases): a non-object root (array, string, number, bool, null), a missing or non-"2.0" jsonrpc member, a method that is not a present non-empty string (absent, non-string, or empty-string "" - a whitespace-only string is a valid method -> -32601, not -32600), a present-but-invalid id whose JSON type is not string or number (object, array, bool, null - MCP 2026-07-28 RequestId permits only string|number), AND a present numeric id that is not finite (a JSON-syntactically-valid overflow literal such as 1e400 / -1e400 that json.loads parses to float('inf')/-inf, which parse_constant does NOT catch - so the id-type guard's math.isfinite() clause rejects it) each return -32600 Invalid Request - distinct from -32700 (bad JSON) and -32601 (well-formed request, unknown method). For the invalid-id cases the -32600 frame MUST carry id:null (the malformed/non-finite id is NEVER echoed into the response). CRITICAL id-absent-malformed rows (parametrized, in-place; cycle-16 Finding A): a MALFORMED payload that ALSO lacks an id - a non-object root ([], 42, "s", true, null), a bad/missing jsonrpc, OR a method that is not a present non-empty string (canonically {"jsonrpc":"2.0"} with no method and no id; AND the empty-string variant {"jsonrpc":"2.0","method":""} with no id) - returns -32600 with id:null and is NOT suppressed. Suppression (silence) is reserved for an OTHERWISE-VALID request that merely lacks an id (the notification scenario below). This binds the ORDERING INVARIANT: request-shape validation (root/jsonrpc/method/id-type) runs BEFORE the id-absent notification-suppression branch in dispatch(), so an absent id never rescues a malformed payload from -32600. A present null id remains a -32600 invalid request, not a notification.
- id-less notification silence (parametrized): an OTHERWISE-VALID request lacking an id is silent (no response frame) - proven for both a known method (notifications/initialized) AND an unknown method (JSON-RPC 2.0: a notification receives NO response even on method-not-found). This is the deliberate counterpart to the id-absent MALFORMED -32600 rows above; the two together prove shape-validation precedes notification-suppression (a valid no-id request is silenced; a malformed no-id payload is -32600/id:null).
- Response-id echo + id-absence-by-membership (parametrized rows, cycle-16 Finding A): (i) a -32600 caused by a NON-id defect while a VALID present id is supplied (e.g. {"jsonrpc":"2.0","id":5} with a missing method) ECHOES that id (id:5), NOT id:null - id:null is reserved for an absent or itself-malformed/non-finite id (a non-object root cannot carry an id, so it stays id:null); (ii) id-absence is decided by KEY MEMBERSHIP, not truthiness - a request carrying id:0 (and id:"") receives a NORMAL echoed response (id:0 / id:""), never silent suppression, guarding against a `not message.get("id")` truthiness bug that would silently drop id:0 responses while passing all id:1/string-id rows.
