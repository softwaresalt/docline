Author the failing intermediate-redirect-body drain harness in the fetch test suite (tests/fetch/) (test-first / red). Tests domain only. Cycle-10 (PR #166 round-3 review) found the per-response streamed cap (064.013-T) and the aggregate during-read budget (064.017-T/064.024-T) only bound the FINAL response returned by opener.open() - they replace the terminal response.read() but NOT the intermediate 3xx bodies drained INSIDE urllib's HTTPRedirectHandler. urllib.request.HTTPRedirectHandler.http_error_302 (aliased to 301/303/307/308) calls an UNBOUNDED fp.read() on each intermediate 3xx response body before opener.open() returns, so a hostile server can return a chain of 3xx responses whose intermediate bodies are arbitrarily large (or many under-cap bodies) and exhaust memory/network while BYPASSING both the per-response MAX_RESPONSE_BYTES cap and the request-scoped aggregate MAX_TOTAL_FETCH_BYTES budget. This harness pins that the intermediate 3xx bodies are bounded-read/drained and COUNTED against the SAME per-response and aggregate allowances on the SHARED fetch code (affects CLI docline fetch and the MCP fetch tool). See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H7 item 2, "intermediate redirect bodies").

<!-- BEGIN:acceptance-criteria -->
- Per-response intermediate-body cap (always-on, single fetch), parametrized across redirect status codes 301/302/303/307/308: a redirect chain whose INTERMEDIATE 3xx response body exceeds MAX_RESPONSE_BYTES = 10 MiB (10485760 bytes) is aborted with the typed cap error WITHOUT fully buffering that intermediate body - proving the intermediate body goes through the SAME bounded reader as the final response, not urllib's unbounded fp.read(). Parametrizing over ALL FIVE redirect codes (added as rows to this ONE scenario, not new scenarios) proves the impl rebinds the http_error_301/303/307/308 aliases to the bounded override and does not leave 4 of the 5 codes on the base unbounded handler. Exact-boundary over-read guard: via a fake/instrumented transport recording every read size on the intermediate 3xx fp, the harness asserts the reader consumes AT MOST MAX_RESPONSE_BYTES + 1 total bytes (only the single crossing byte) before aborting - NOT MAX_RESPONSE_BYTES + CHUNK_SIZE - and that each individual read request on the intermediate body is bounded by min(CHUNK_SIZE, remaining_response_bytes + 1).
- Aggregate intermediate-body accounting (crawl-scoped budget): with the request-scoped RemainingByteBudget seeded LOW (or pre-consumed by prior in-crawl fetches - urllib's default max_redirects = 5 makes a single chain of under-10-MiB bodies unable to reach 512 MiB, so the harness proves the DECREMENT/cross-remaining behavior hermetically rather than accumulating a real 512 MiB), an intermediate 3xx redirect body whose bytes cross the REMAINING aggregate allowance is aborted mid-drain - proving each intermediate 3xx body decrements the SAME request-scoped remaining-byte budget (seeded by crawl(), threaded through fetch_page) EVEN WHILE REDIRECTING (redirect bytes are not free), and that AggregateBudgetExceededError propagates out of crawl() as a RAISE (not a per-page skipped CrawlResult). The crossing intermediate body transfers at most one additional (crossing) byte (each read min(CHUNK_SIZE, per_response_remainder + 1, aggregate_remainder + 1)).
- Redirect function preserved: a redirect chain whose intermediate bodies are ALL within the per-response and aggregate allowances still follows normally to its final response and returns the expected FetchResponse (the bounded drain reads+counts the intermediate body, then proceeds to the Location target) AND the §H6 per-redirect revalidation + max_redirects count still run (the drain is folded into the existing _ValidatingRedirectHandler, one composite handler) - the cap hardening does NOT break legitimate redirects or weaken H6.
- All new tests observed FAILING before implementation (red) - the intermediate 3xx bodies are currently drained by urllib's unbounded fp.read() with no cap and no budget decrement.
- Scenario budget: 3 (per-response intermediate-body cap [parametrized over 301/302/303/307/308], aggregate intermediate-body accounting, redirect-still-follows) - within the <4 heuristic.
