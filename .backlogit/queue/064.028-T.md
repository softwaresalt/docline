Make 064.027-T green. Code domain only, <=1 file (src/docline/fetch/http.py). EXTEND the EXISTING single redirect handler _ValidatingRedirectHandler (src/docline/fetch/http.py:41, a request.HTTPRedirectHandler subclass ALREADY installed on the opener built in fetch_page's _fetch() at line 119-120, which overrides redirect_request() for §H6 per-redirect revalidation + the max_redirects count) so every intermediate 3xx response body is bounded-read/drained through the SAME bounded reader as the final response - against BOTH the per-response MAX_RESPONSE_BYTES cap AND the request-scoped aggregate MAX_TOTAL_FETCH_BYTES budget - instead of urllib's default unbounded fp.read() inside HTTPRedirectHandler.http_error_302. Cycle-12 (PR #166 Copilot cycle-3 Finding A): the override MUST also guarantee INTERMEDIATE-RESPONSE RESOURCE CLOSURE. When the bounded proxy raises a per-response OR aggregate cap error MID-STREAM (inside stdlib http_error_302's fp.read()), stdlib never reaches its own fp.close() (it closes AFTER a completed read), so the underlying intermediate 3xx response fp - a live socket/connection - LEAKS. The override wraps the super() delegation in a guard that CLOSES the real intermediate fp before re-raising the typed cap error, on BOTH breach paths. The redirect-HOP MAX_FETCH_ATTEMPTS debit is NO LONGER owned here - it is DECOMPOSED into the width-isolated pair 064.029-T (harness) / 064.030-T (impl), which places the debit inside redirect_request on the successful next-request path (after §H6/stdlib validation, before outbound I/O). Do NOT install a SECOND redirect handler: urllib's OpenerDirector dispatches a given http_error_NNN to handlers in order and stops at the first that returns a response, so two redirect handlers cannot both run (one would bypass either H6 validation or the bounded drain) - the drain MUST be folded into the existing _ValidatingRedirectHandler as ONE composite handler. Hardens BOTH interfaces (CLI docline fetch and the MCP fetch tool) - a cross-interface behavior change (see plan Rollback/Risks/SA-1). This task does NOT introduce new numeric caps (it reuses MAX_RESPONSE_BYTES from 064.013-T and MAX_TOTAL_FETCH_BYTES/RemainingByteBudget/AggregateBudgetExceededError from 064.017-T) and does NOT change app_models.py or fetch/crawl.py. Split out of 064.013-T/064.017-T because the redirect-handler override is additional width AND the intermediate-body drain must decrement the request-scoped aggregate budget that only exists after 064.017-T/064.024-T. See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H7 item 2, "intermediate redirect bodies"; cycle-10 remediation; cycle-12 resource-closure hardening + redirect-attempt decomposition).

- fetch/http.py extends the existing _ValidatingRedirectHandler with an http_error_302 override AND rebinds ALL redirect-code aliases to it: `http_error_301 = http_error_303 = http_error_307 = http_error_308 = http_error_302` INSIDE the subclass. This is REQUIRED because urllib defines http_error_301/303/307/308 as class-level aliases of the BASE http_error_302; a subclass that overrides only http_error_302 leaves 301/303/307/308 bound to the BASE unbounded handler (verified: Sub.http_error_301 is base http_error_302), so those redirect codes would still drain with an unbounded fp.read(). The override bounded-reads/drains each intermediate 3xx body via the SAME bounded reader used for the final response, capping each individual read at min(CHUNK_SIZE, per_response_remainder + 1, aggregate_remainder + 1), counting the ACTUAL bytes read, and decrementing BOTH a FRESH per-response MAX_RESPONSE_BYTES allowance (reset each redirect hop - each intermediate 3xx response is a separate response) AND the shared request-scoped aggregate RemainingByteBudget (persistent across the whole request; threaded when a crawl budget is present) by that count - so intermediate redirect bytes are COUNTED even while redirecting. Recommended minimal-risk technique: wrap the intermediate `fp` in a bounded-reading proxy whose .read() counts+caps against both allowances, then delegate to super().http_error_302(req, wrapped_fp, code, msg, headers) so the existing _ValidatingRedirectHandler.redirect_request (§H6 revalidation + max_redirects count) and the stdlib Location resolution / loop detection / scheme check still run unchanged and the redirect still follows (do NOT reimplement the method body). The per-response allowance and the optional aggregate RemainingByteBudget are passed into _ValidatingRedirectHandler.__init__ (it is constructed per fetch_page call at http.py:119, where the fetch_page-threaded budget from 064.017-T is in scope).
- Intermediate-response CLOSURE on breach (cycle-12, Finding A): the override guarantees the underlying intermediate 3xx response fp is CLOSED before any typed cap error propagates, on BOTH the per-response and aggregate breach paths - because the bounded proxy raises MID-STREAM inside stdlib http_error_302's fp.read(), stdlib never reaches its own fp.close() (which runs only AFTER a completed read), so without this guarantee the intermediate socket/connection leaks. Minimal-risk technique: wrap the super().http_error_302(...) delegation in `try: ... except AggregateBudgetExceededError: fp.close(); raise` and an equivalent guard for the per-response cap error (the per-response cap error is caught first / alongside), closing the REAL intermediate fp (not just the proxy) exactly once before re-raising. Because FetchAttemptBudgetExceededError subclasses AggregateBudgetExceededError, this SAME guard also releases the fp when 064.030-T's redirect_request attempt debit raises - so closure holds across all typed budget/cap breaches without duplicating close logic. fp.close() is idempotent, so a redundant close on any path is a no-op. SCOPE (matches Finding A's "both failures"): the guard closes fp on the two body-drain cap breaches (and the subclassed attempt breach). Other non-follow exits are outside Finding A's scope and retain their existing handling: the stdlib SCHEME and LOOP-detection rejections raise HTTPError that CARRIES the fp per the stdlib contract (bounded by max_redirects; the documented cycle-10 unread-fp residual in plan Risks), and a §H6-revalidation rejection from redirect_request is pre-existing behavior. The impl MAY broaden the cleanup to also release fp on those non-stdlib-HTTPError exits, but this task does NOT expand the harness beyond the two cap-breach closure assertions.
- Per-response breach: an intermediate 3xx body exceeding MAX_RESPONSE_BYTES = 10 MiB (10485760 bytes) aborts the drain MID-STREAM by raising the typed per-response cap error the instant a read returns a byte beyond 10485760 (the over-cap intermediate body is never fully buffered; the over-cap transfer is at most MAX_RESPONSE_BYTES + 1, never + CHUNK_SIZE) AND the intermediate fp is closed before the error propagates. Applies to a single fetch (per-response cap is always-on) even when no crawl aggregate budget is threaded.
- Aggregate breach: when crawl() has seeded a request-scoped RemainingByteBudget (064.017-T), each intermediate 3xx body decrements that SAME budget while chunks are read; crossing the aggregate allowance raises AggregateBudgetExceededError mid-drain (a DoclineError subclass) AND the intermediate fp is closed before the error propagates, which propagates out of crawl() as a RAISE (not a per-page skipped CrawlResult). The budget defaults to unbounded/None for a standalone single fetch, so existing CLI single-fetch callers keep working.
- Redirect function preserved: redirect chains whose intermediate bodies stay within the per-response and aggregate allowances follow normally to the final response (the drained-and-counted intermediate body then proceeds to the Location target), and the §H6 SSRF-by-resolution address-pinned connect / per-redirect revalidation is NOT weakened - because the drain is folded INTO the existing _ValidatingRedirectHandler (ONE composite handler, not a second handler), its redirect_request (§H6 revalidation + max_redirects count, default 5) still runs for every hop via super().http_error_302.
