Implement the request-scoped fetch-attempt budget on the SHARED fetch code to turn 064.025-T green. Code domain only, <=2 files (src/docline/fetch/http.py + src/docline/app_models.py). Cycle-11 (PR #166) REPLACES the rejected frontier-pop cap (a counter in fetch/crawl.py incremented only on main-page pops, which left robots/TOC/retries/redirects uncounted) with a request-scoped ATTEMPT budget enforced at the COMMON outbound-fetch boundary `fetch_page`: (1) src/docline/fetch/http.py - seed a per-request fetch-attempt allowance MAX_FETCH_ATTEMPTS = 4 * MAX_PAGES_LIMIT = 4000 on the SAME request-scoped budget object (`RemainingByteBudget`, introduced by 064.017-T and already threaded through EVERY `fetch_page` call by 064.017-T/064.024-T); `fetch_page` debits ONE attempt BEFORE each direct outbound request (pre-I/O), RAISING `FetchAttemptBudgetExceededError` (a subclass of `AggregateBudgetExceededError`, so the four existing `except AggregateBudgetExceededError: raise` clauses in crawl.py propagate it out of `crawl()` - no new crawl.py re-raise) the instant a debit would exceed the cap; redirect hops (followed inside opener.open()) are NOT debited here - they are debited per-hop inside the shared `_ValidatingRedirectHandler` (in redirect_request, after §H6/stdlib validation, before outbound I/O) by 064.030-T (see below); (2) src/docline/app_models.py - FetchRequest.depth gains a hard upper bound Field(default=0, ge=0, le=64) (MAX_DEPTH_LIMIT; default preserved so depth stays optional). Because every direct outbound request (main pages, robots via `_robots_allow`, TOC via `_discover_toc_links`, per-pop retries via `_fetch_with_retries` - each a distinct `fetch_page` call) passes through the `fetch_page` choke point, and every redirect hop passes through the shared `_ValidatingRedirectHandler` (debited by 064.030-T), auxiliary/retry/redirect traffic cannot exceed MAX_FETCH_ATTEMPTS. Hardens BOTH interfaces (CLI docline fetch and the MCP fetch tool) - a cross-interface behavior change (see plan Rollback/Risks). Does NOT own the per-response or aggregate BYTE budgets (064.013-T / 064.017-T / 064.024-T) - those bound transfer VOLUME; this bounds request COUNT. No fetch/crawl.py edit - the frontier-pop counter is removed; threading and abort-propagation are inherited from 064.017-T/064.024-T. See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H7 item 4, cycle-11).

<!-- BEGIN:acceptance-criteria -->
- fetch/http.py enforces a per-request fetch-attempt bound via a named module constant MAX_FETCH_ATTEMPTS = 4 * MAX_PAGES_LIMIT = 4000. The request-scoped budget object (`RemainingByteBudget` from 064.017-T) gains a fetch-attempt allowance seeded at MAX_FETCH_ATTEMPTS per crawl request. `fetch_page` performs a checked debit: one attempt debited BEFORE initiating each direct outbound request (so main-page fetches, robots.txt (`_robots_allow`), mdBook TOC-script fetches (`_discover_toc_links`), and per-pop retries - each a distinct `fetch_page` call via `_fetch_with_retries` - each count exactly one; pre-I/O). Redirect hops (followed inside `opener.open()`) are debited SEPARATELY, one per hop INSIDE the shared `_ValidatingRedirectHandler` in redirect_request (after §H6/stdlib validation, immediately before returning a non-None Request - so rejected redirects consume no attempt), and are owned by 064.030-T (harness 064.029-T; NOT via a post-open `handler.redirect_count` tally, which is observability-only). Crossing MAX_FETCH_ATTEMPTS aborts by RAISING `FetchAttemptBudgetExceededError` (a `DoclineError` subclass that subclasses `AggregateBudgetExceededError`; no bare except) - it does NOT silently return the accumulated skipped results. Because the abort type subclasses `AggregateBudgetExceededError`, the four `except AggregateBudgetExceededError: raise` clauses already in crawl.py (064.017-T/064.024-T) propagate it out of `crawl()` with NO new crawl.py edit. Boundary: the first 4000 debits succeed; the debit that would cross the cap is refused BEFORE its outbound I/O.
- app_models.py: FetchRequest.depth gains a hard upper bound MAX_DEPTH_LIMIT = 64 (Field(default=0, ge=0, le=64) - the existing default=0 is PRESERVED so depth stays optional and is NOT made required); depth 0..64 inclusive accepted, >= 65 raises ValidationError (surfaces as -32602 on the MCP boundary), and a request omitting depth still validates (defaults to 0). depth flows into CrawlConfig.max_depth (app.py:606), so the model bound closes the untrusted-input depth vector at the boundary.
- 064.025-T harness passes green (outbound-attempt budget incl. robots/TOC/retry boundary coverage + depth upper bound; the redirect-hop attempt coverage is green under 064.029-T/064.030-T).
- The existing tests/fetch suite remains green under the new bounds: the fetch-attempt allowance defaults to the shared hard cap for a crawl request and to unbounded/None for a standalone single fetch so existing CLI single-fetch callers are unaffected (or is deliberately updated for the new limits, documented in the commit). Typed errors only; no bare except.
- No fetch/crawl.py change: the rejected frontier-pop counter and loop-guard edit are removed; the request-scoped budget threading (064.017-T/064.024-T) and its four `except AggregateBudgetExceededError: raise` clauses are reused unchanged.
