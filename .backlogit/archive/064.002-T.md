<!-- BEGIN:acceptance-criteria -->
- src/docline/mcp/stdio.py provides pure dispatch(message, server) and serve(stdin, stdout, server=SERVER), reserving real stdout for JSON-RPC frames; clean EOF exit. serve() reads frames with a NON-GREEDY input primitive (`read1` on the injected stdin stream - equivalently os.read on a raw fileno) that returns as soon as ANY bytes are available and never blocks waiting to fill a whole CHUNK_SIZE, and EXPLICITLY FLUSHES stdout after writing EVERY response frame - so an interactive client that sends one frame, waits for its response, then sends the next (with stdin still open; the 064.008-T live smoke test) never deadlocks. Because the primitive is `read1`/`flush` on the INJECTED stdin/stdout stream objects (not a hardcoded raw global fileno), the in-process instrumented liveness assertion in 064.001-T can drive and observe it directly. A greedy read(CHUNK_SIZE) that waits for the full chunk after a short frame, or a block-buffered stdout that withholds the response until the pipe closes, would live-lock that probe (cycle-8) and fail 064.001-T's in-process liveness assertion as well as the 064.008-T subprocess smoke.
- dispatch() performs JSON-RPC request-shape validation returning -32600 Invalid Request for a non-object root, a missing/invalid jsonrpc member, a method that is not a present non-empty string (the SINGLE method predicate: present AND string AND non-empty - absent/non-string/empty "" -> -32600; a whitespace-only string is a valid method -> -32601), or a present id whose JSON type is not string or number (object/array/bool/null rejected - MCP 2026-07-28 RequestId permits only string|number) - distinct from -32700 (bad JSON) and -32601 (unknown method). Response-id rule: the -32600 frame carries id:null ONLY when the id is undetectable (absent, or itself malformed/non-finite); a VALID present id (string/finite number) accompanying a NON-id defect (missing/empty method, bad/missing jsonrpc) is ECHOED in the -32600 frame (a non-object root cannot carry an id, so it stays id:null). ORDERING INVARIANT (cycle-16 Finding A): request-shape validation (root/jsonrpc/method/id-type only - params structural validation is POST-suppression and applies only to id-bearing requests -> -32602) runs BEFORE the id-absent notification-suppression branch, so an ABSENT id yields silence ONLY when the payload is OTHERWISE VALID (object root, jsonrpc "2.0", non-empty string method) - a true JSON-RPC notification, silent even for an unknown method OR malformed params; an absent id on a MALFORMED payload (non-object root, bad/missing jsonrpc, or missing/non-string/empty method - canonically {"jsonrpc":"2.0"} with no method and no id) does NOT suppress the response but returns -32600 with id:null. Id-absence is decided by KEY MEMBERSHIP ("id" not in message), NOT truthiness: a present id:0 or id:"" is a valid RequestId that receives a normal echoed response, never silent suppression. A present null id is a -32600 invalid request, not a notification.
- Strict JSON parsing rejects non-finite constants (H2/framing integrity, cycle-10 review round-3): the frame parse (json.loads in serve()/the frame reader, before dispatch()) MUST pass a parse_constant callback that REJECTS Python's permissive JSON-extension TOKENS NaN, Infinity, and -Infinity, mapping the rejection to a -32700 parse error (invalid JSON per RFC 8259 / JSON-RPC 2.0) - NOT accepting them as float. This runs BEFORE the id-type guard and BEFORE era routing. HOWEVER, parse_constant does NOT fire for numeric LITERALS that OVERFLOW to infinity: json.loads("1e400") returns float('inf') WITHOUT invoking parse_constant (verified). So the request-shape id guard MUST ALSO reject a present numeric id that is not finite: for a float id, require math.isfinite(id) - a non-finite numeric id (e.g. from 1e400 / -1e400) is an invalid RequestId -> -32600 with id:null (never echoed), consistent with the other invalid-id cases. Together the two guards ensure NO non-finite number (token form or overflow form) can enter RequestId or reach json.dumps (which would otherwise re-emit the bare non-JSON token NaN/Infinity/-Infinity and corrupt the frame). Both eras inherit both guards (parse + shape validation precede _meta extraction / era classification). Defense-in-depth: the response serializer MUST use allow_nan=False so a stray non-finite raises internally, and any such serialization ValueError degrades to a -32603 internal-error envelope (or is dropped for a notification) rather than terminating the serve loop - it MUST NOT crash the transport. The parse_constant is a kwarg on the SAME single json.loads call and the finite-id check is an additional inline clause in the SAME dispatch() request-shape guard - no new function, no new file; the <=4-function transport budget holds.
- Legacy-era method map: initialize (capabilities + protocolVersion 2025-11-25 + serverInfo, all sourced from the adapter describe_server() accessor introduced by 064.015 - NOT hardcoded in stdio.py, so the transport stays a pure translator and the identity single-source invariant holds from first commit); notifications/initialized silent; ping -> {}; tools/list via server.list_callable_tools(); tools/call via server.call_tool; id-less notification silent; and dispatch()'s tools/call handler shapes every tools/call return (fetch/process/export_schema) INLINE into a standards-valid MCP CallToolResult - result.content is a non-empty ContentBlock[] (typed text block(s)), result.structuredContent mirrors the domain result when applicable, and success=False -> isError=true with sanitized error text carried in content - NOT the raw FetchResult/ProcessResult/str serialized directly. The modern branch (064.022) REUSES this same dispatch output and applies only the resultType wrapper on top, so both eras emit the identical CallToolResult body (no per-era drift, no extra transport function).
- Bounded binary frame read/drain helper AND its runtime enforcement (H2): fixed-chunk reads (each via the NON-GREEDY read1/os.read primitive, returning available bytes without blocking to fill the chunk) up to `MAX_FRAME_BYTES = 1 * 1024 * 1024 = 1_048_576` payload bytes (named module constant; plan §H2 Selected numeric limit) scanning for the newline, bounded drain of an oversized/unterminated frame - NOT a post-read length check on an unbounded readline(). Exact boundary (`MAX_FRAME_BYTES` counts payload bytes BEFORE the `\n`, delimiter excluded): a frame of up to and including exactly `1_048_576` payload bytes + `\n` is accepted and dispatched (exact-N); each read is capped at `min(CHUNK_SIZE, MAX_FRAME_BYTES - buffered_payload + 1)` so at the boundary the reader observes at most the single crossing byte (buffered content <= `MAX_FRAME_BYTES + 1`, never a full extra CHUNK_SIZE chunk); payload byte N+1 with no `\n` overflows -> discard the oversized accumulation, emit an error envelope, drain the remainder in bounded CHUNK_SIZE chunks to the next `\n`/EOF, and resynchronize on the next valid frame. A carry-over buffer preserves any bytes read AFTER a frame's newline terminator (a fixed-size read can return a newline plus the head of the next frame) and seeds the next frame from them, in BOTH the normal-frame path AND the oversized-drain path, so a following JSON-RPC request in the same chunk is never dropped. RecursionError/ValueError degrade to an envelope.
