Implement the per-dimension resource-exhaustion caps on the SHARED fetch code to turn 064.012-T green. Code domain only. Two minimal edits: (1) app_models.py hard max_pages upper bound; (2) fetch/http.py streamed MAX_RESPONSE_BYTES read replacing the unbounded response.read() (the initial response AND the FINAL response opener.open() returns after following redirects). Hardens BOTH interfaces (CLI docline fetch and the MCP fetch tool) - a cross-interface behavior change (see plan Rollback/Risks). NOTE (cycle-10): the bounded reader here replaces only the TERMINAL response.read() (the response opener.open() returns); the INTERMEDIATE 3xx redirect bodies drained INSIDE urllib's HTTPRedirectHandler (its own unbounded fp.read() before opener.open() returns) are a SEPARATE choke point owned by the width-isolated pair 064.027-T (harness) / 064.028-T (extends the existing _ValidatingRedirectHandler with a bounded drain + all-alias rebind) - do NOT claim this task covers intermediate redirect bodies. This task does NOT own the aggregate MAX_TOTAL_FETCH_BYTES budget: that budget is a separate width-isolated pair (064.016-T/064.017-T) and is enforced by a request-scoped remaining-byte budget THREADED into fetch_page and decremented while chunks are read across retries and ancillary (robots.txt/TOC) fetches - NOT by a post-return loop accumulator that only sees successful FetchResponse objects (a loop accumulator cannot see bytes consumed by over-cap attempts that raise and retry, nor ancillary fetches). This task also does NOT own the request-amplification bound (the fetch-attempt/frontier counter in fetch/crawl.py + the FetchRequest.depth upper bound): that is a separate width-isolated pair (064.025-T harness / 064.026-T impl) split out at cycle-8 so this task stays pinned to its 2 files (app_models.py max_pages + fetch/http.py byte cap) - the fetch-attempt counter lives in fetch/crawl.py, a third file. See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H7).

<!-- BEGIN:acceptance-criteria -->
- FetchRequest.max_pages gains a hard upper bound MAX_PAGES_LIMIT = 1000 (Field(ge=1, le=1000)); values 1..1000 inclusive are accepted, an over-limit value (>=1001) raises ValidationError (surfaces as -32602 on the MCP boundary). Bound sized above legitimate CLI crawl use (20x the current CrawlConfig.max_pages default of 50; see plan §H7 Selected numeric limits). None still means "use the crawler default of 50".
- fetch/http.py reads the body in bounded chunks (replacing the unbounded response.read()) and enforces MAX_RESPONSE_BYTES = 10 MiB (10485760 bytes) EXACTLY by capping each individual read size at min(CHUNK_SIZE, remaining_response_bytes + 1), where remaining_response_bytes = MAX_RESPONSE_BYTES - bytes_read_so_far. Because a read is never requested larger than the remaining allowance plus one, at the boundary only the SINGLE crossing byte can be pulled from the socket - NOT a full extra CHUNK_SIZE chunk. The reader aborts with a typed error the instant a read returns a byte beyond 10485760. Applies to the initial response AND the terminal response opener.open() returns after following any redirects. (The INTERMEDIATE 3xx redirect bodies drained inside urllib's HTTPRedirectHandler are bounded/counted by the separate pair 064.027-T/064.028-T, not this task.) Boundary: exactly 10485760 raw bytes are allowed and buffered; the read that would exceed the cap transfers at most one additional (crossing) byte, is aborted mid-stream, and the over-cap response is never fully buffered.

- The existing tests/fetch suite remains green under the new bounds (or is deliberately updated for the new limit, documented in the commit). Typed errors only; no bare except.
