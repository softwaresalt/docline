Author the failing intermediate-redirect-body drain harness in the fetch test suite (tests/fetch/) (test-first / red). Tests domain only. Cycle-10 (PR #166 round-3 review) found the per-response streamed cap (064.013-T) and the aggregate during-read budget (064.017-T/064.024-T) only bound the FINAL response returned by opener.open() - they replace the terminal response.read() but NOT the intermediate 3xx bodies drained INSIDE urllib's HTTPRedirectHandler. urllib.request.HTTPRedirectHandler.http_error_302 (aliased to 301/303/307/308) calls an UNBOUNDED fp.read() on each intermediate 3xx response body before opener.open() returns, so a hostile server can return a chain of 3xx responses whose intermediate bodies are arbitrarily large (or many under-cap bodies) and exhaust memory/network while BYPASSING both the per-response MAX_RESPONSE_BYTES cap and the request-scoped aggregate MAX_TOTAL_FETCH_BYTES budget. This harness pins that the intermediate 3xx bodies are bounded-read/drained and COUNTED against the SAME per-response and aggregate allowances on the SHARED fetch code (affects CLI docline fetch and the MCP fetch tool). Cycle-12 ALSO pins intermediate-response RESOURCE OWNERSHIP (PR #166 Copilot cycle-3 Finding A): when a per-response OR aggregate cap breach interrupts the bounded read MID-STREAM, the underlying intermediate 3xx response fp (a live socket/connection) MUST be CLOSED before the typed cap error propagates - CPython's stdlib HTTPRedirectHandler.http_error_302 only calls fp.close() AFTER its fp.read() returns, so a mid-read raise from the bounded proxy leaks the intermediate connection. This harness asserts closure on the per-response AND aggregate cap-breach paths AND on the two redirect_request-raised custom exits (redirect-cap FetchError, §H6 CrawlUrlRejectedError), which - unlike stdlib HTTPError - do not carry the fp and are raised BEFORE stdlib reaches its fp.read()/fp.close(), so they leak the intermediate connection identically. The redirect-HOP fetch-attempt accounting is NO LONGER pinned here - it is DECOMPOSED into the width-isolated pair 064.029-T (harness) / 064.030-T (impl), which proves the debit is placed correctly inside redirect_request on the successful next-request path (after policy validation, before outbound I/O). See docs/plans/2026-08-27-mcp-stdio-server-plan.md (Plan Hardening H7 item 2 "intermediate redirect bodies"; cycle-10 remediation; cycle-12 resource-closure hardening + redirect-attempt decomposition).

Parametrizing over ALL FIVE redirect codes (added as rows to this ONE scenario, not new scenarios) proves the impl rebinds the http_error_301/303/307/308 aliases to the bounded override and does not leave 4 of the 5 codes on the base unbounded handler. RESOURCE-CLOSURE assertion (cycle-12, Finding A): the instrumented intermediate fp also records .close() calls, and the harness asserts the underlying intermediate 3xx response fp is CLOSED (exactly once) when the per-response cap error propagates - proving the mid-read raise does NOT leak the intermediate connection (stdlib http_error_302 would only fp.close() AFTER a completed fp.read(), which never returns on breach).

RESOURCE-CLOSURE assertion (cycle-12, Finding A): the instrumented intermediate fp asserts the underlying intermediate 3xx response fp is CLOSED (exactly once) when the aggregate cap error propagates mid-drain - the aggregate-breach path must not leak the intermediate connection any more than the per-response-breach path. This proves the guard owns the real fp on redirect_request-raised exits, not only on the body-drain cap breaches.
