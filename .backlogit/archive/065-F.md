Chore (security hardening) covering feature. Extend the shared sitemap SSRF classifier `_is_unsafe_address` (`src/docline/fetch/sitemap.py:173-189`) to reject Carrier-grade NAT (CGNAT) shared address space `100.64.0.0/10` (RFC 6598) via an explicit network-membership check. None of the six `ipaddress` flags (`is_private`, `is_loopback`, `is_link_local`, `is_multicast`, `is_reserved`, `is_unspecified`) catch that range on Python 3.12.x, so the current six-flag reject-list lets it through. Origin: PR #166 Copilot review thread `PRRT_kwDOSsAX4c6dXgJs` (comment 3885656388); the `docs/plans/2026-08-27-mcp-stdio-server-plan.md` `## Risks` tracked-follow-up bullet had no backlog item. This feature makes the fix real, queued, high-priority, and dependency-aware so it cannot be lost. Mirrors the §H6 fetch-path CGNAT fix (feature 064-F / url_policy) on the pre-existing sitemap surface.

Activation condition (dependency-aware trigger): the gap is DORMANT today — `validate_sitemap_url`/`_is_unsafe_address` has ZERO production callers (independently traced: the live CLI+MCP crawl path routes mcp/server.py->app.execute_fetch->elt.execute->fetch.crawl->fetch.http->url_policy.validate_crawl_url, and robots handling uses RobotFileParser.can_fetch, never discover_sitemaps_from_robots). It goes LIVE the moment any future shipment wires sitemap discovery (`validate_sitemap_url` / `discover_sitemaps_from_robots`) into the crawl path; any such shipment MUST carry a dependency on THIS feature (065-F) so the CGNAT fix lands before/with it. Because the gap is dormant and §H6 uses an independent complete classifier, 065-F carries NO blocking dependency on 064-F/055-S and does NOT delay 055-S.

Drift risk (accepted, deferred — deliberation Option B): after §H6 the codebase holds two independent SSRF address classifiers — `url_policy` (resolve + address-pin, WITH explicit CGNAT) and `sitemap._is_unsafe_address` (six flags, WITHOUT CGNAT until this lands). Divergent reject-lists are a known SSRF footgun; the durable fix is to consolidate onto ONE shared unsafe-address predicate (H6 classifier as source of truth). Tracked as a follow-up, not required to close this finding.

<!-- BEGIN:dod -->
- `_is_unsafe_address("100.64.0.1")` (and other addresses in `100.64.0.0/10`, including the range boundaries `100.64.0.0` and `100.127.255.255`) returns `True` via an explicit `ipaddress` network-membership check against a module-level `_CGNAT_NETWORK = ipaddress.ip_network("100.64.0.0/10")`.
- IPv4-mapped IPv6 literals are normalized to their embedded IPv4 BEFORE the six-flag classification and the CGNAT check (guarded for `IPv6Address` only; membership guarded by `ip.version == 4`), so `_is_unsafe_address("::ffff:100.64.0.1")` returns `True` and `validate_sitemap_url("http://[::ffff:100.64.0.1]/sitemap.xml")` raises `SitemapError` — mirroring the §H6 "normalize IPv4-mapped IPv6 first" requirement. Non-mapped IPv4/IPv6 inputs are unchanged; the deprecated IPv4-compatible `::/96` form is not reinterpreted.
- `validate_sitemap_url` rejects a CGNAT IP-literal URL and a host that resolves (via `getaddrinfo`) into `100.64.0.0/10` (DNS-rebinding style: reject if ANY resolved address is CGNAT), raising `SitemapError`.
- Public-unicast addresses and the just-below/above boundaries (`100.63.255.255`, `100.128.0.0`, and the IPv4-mapped `::ffff:100.63.255.255`) stay ACCEPTED — the fix does not over-reject.
- Tests pin the CGNAT class directly (assert `_is_unsafe_address` result), not the `ipaddress` flag table, since special-purpose tables are Python-patch-dependent (CVE-2024-4032).
- Red-before-green: `065.001-T` observed failing before `065.002-T` implements the check; all pre-existing `tests/fetch/test_sitemap.py` rows stay green.
- Quality gates green: `ruff check .`, `ruff format --check .`, `pyright src/`, `pytest tests/fetch/test_sitemap.py`.
- No blocking dependency on `064-F`/`055-S`; touches only `src/docline/fetch/sitemap.py` + `tests/fetch/test_sitemap.py` (disjoint from the §H6 files), so no merge-order conflict.
