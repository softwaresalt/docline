Author the failing CGNAT `100.64.0.0/10` (RFC 6598) rejection harness in `tests/fetch/test_sitemap.py` (test-first / red). Tests domain only. Extends the existing SSRF suite (which currently covers loopback/private/link-local/metadata but NOT CGNAT). Grounds in `src/docline/fetch/sitemap.py` `_is_unsafe_address` (lines ~173-189) and `validate_sitemap_url`. See `docs/plans/2026-08-28-sitemap-cgnat-ssrf-gap-plan.md`.

<!-- BEGIN:acceptance-criteria -->
- Class-pin (parametrized): `_is_unsafe_address(addr)` returns `True` for CGNAT addresses `100.64.0.1`, `100.100.100.100`, `100.127.255.255`, the range boundaries `100.64.0.0` and `100.127.255.255`, AND the IPv4-mapped IPv6 literal form `::ffff:100.64.0.1` (which normalizes to `100.64.0.1`). Assert the classifier RESULT directly (pin the class), NOT the `ipaddress` flag table, since special-purpose tables are Python-patch-dependent (CVE-2024-4032).
- IP-literal URL rejection (parametrized): `validate_sitemap_url("http://100.64.0.1/sitemap.xml")` (and `https://100.127.255.255/sitemap.xml`, AND the bracketed IPv4-mapped IPv6 literal `http://[::ffff:100.64.0.1]/sitemap.xml`) raises `SitemapError` — the literal path (no DNS) rejects CGNAT (including its IPv4-mapped form) before resolution.
- Resolved-host rejection (DNS-rebinding style, monkeypatched `getaddrinfo`): a host resolving to a CGNAT address — and a mixed set where only ONE of several resolved addresses is CGNAT — raises `SitemapError` (reject if ANY resolved address is CGNAT), mirroring the existing rebinding test.
- Boundary/regression ACCEPT rows (parametrized): `_is_unsafe_address("100.63.255.255")`, `_is_unsafe_address("100.128.0.0")`, AND the IPv4-mapped just-below boundary `_is_unsafe_address("::ffff:100.63.255.255")` return `False` (just below/above the /10, incl. the mapped form), and `validate_sitemap_url` accepts a host resolving to a public-unicast address (e.g. `93.184.216.34`) — proving the fix (and the IPv4-mapped normalization) does NOT over-reject and the existing public-accept test stays green.
- All new CGNAT rows observed FAILING before implementation (red); all pre-existing `tests/fetch/test_sitemap.py` rows remain green.
- Scenario budget: <=3 new parametrized scenarios (class-pin, URL/literal+resolved rejection, boundary-accept) — within the <4 heuristic; tests-only / width-compliant. The IPv4-mapped literal rows are added IN-PLACE to the existing class-pin, URL-literal, and boundary-accept scenarios (parametrization widened, no new scenario), so the scenario count stays <=3.

Do NOT implement production code (width isolation) — the `_CGNAT_NETWORK` membership check and the IPv4-mapped normalization are delivered by 065.002-T. Reuse existing patterns in `tests/fetch/test_sitemap.py` (e.g. `test_validate_sitemap_url_rejects_reserved_ip_literals`, `test_validate_sitemap_url_rejects_dns_rebinding_mixed_resolution`, `_FakeGetaddrinfo` monkeypatch style). CGNAT `100.64.0.0/10` reports `is_private`/`is_reserved`/`is_global` all `False` on Python 3.12.x, so the six existing flags miss it — that is exactly the gap these rows expose. The IPv4-mapped literal `::ffff:100.64.0.1` compounds the gap: it parses to an `IPv6Address` that is not a member of the IPv4 `_CGNAT_NETWORK` and whose special-use flags are patch-inconsistent, so it slips past both checks until the normalization lands. Greened by 065.002-T.
